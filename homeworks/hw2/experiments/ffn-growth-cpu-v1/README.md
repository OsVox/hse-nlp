# CPU check: grow our trained model without discarding learned weights

The active selected-scale-v1 training run is unchanged. This preparation does
not authorize or launch another GPU run, choose a new recipe, or establish an
accuracy improvement.

The hypothesis is that short scratch runs may not reveal the benefit of extra
capacity once a smaller model has learned the task. Rather than retrain all
weights, double only the gated feed-forward width from 1,536 to 3,072, keeping
the 512-wide hidden state, attention, tokenizer and 6/4 encoder/decoder depths.
The model grows from 42,481,152 to 66,074,112 parameters. It uses only our own
scratch-trained weights and randomly initialized new input projections.

Old input rows and output columns are copied exactly. New output columns are
zero, so the added units initially contribute zero. Their output weights get
gradients immediately; their input weights get gradients after the first
output-weight update. This follows the idea of function-preserving network
growth discussed in [Net2Net](https://research.google/pubs/net2net-accelerating-learning-via-knowledge-transfer/),
but is not its neuron-duplication algorithm. That paper's results are not
evidence of a quality gain on this task.

Four small CPU tests passed: logits and cached/uncached greedy outputs,
unchanged parent and global random state, learning in added units, and
rejection of non-growth widths. A separate real-checkpoint test passed on four
unchanged original training examples: zero maximum logit difference and equal
32-token greedy sequences with and without cache. The parent file hash was
unchanged. See verification.json for scope and runtime.

These tests do not establish equality on every question, identical dropout
noise during training, GPU speed, or improved accuracy. No grown checkpoint
has been trained, saved as a candidate, or submitted.

If the current continuation stops, a quality test would still need a fixed
time budget, a same-parent baseline, the same original training stream and
full sequences, matched optimizer handling, fixed held-out evaluation, and
Drive exports before bot scoring. Optimizer handling must be decided and
tested explicitly: resetting both arms loses mature moments; extending old
moments requires shape checks and a stated policy for the new coordinates.
Do not silently reset or reuse incompatible optimizer state. A successful
numerical growth check alone is not a reason for a long training run.

## Follow-up: preserve AdamW history

The standalone `grow_adamw_optimizer` helper now copies optimizer groups,
per-tensor step counts and all old moment coordinates; only added coordinates
get zero history. It rejects missing, incompatible or non-CPU state. Six
small tests pass, including an optimizer checkpoint roundtrip and identical
old-coordinate updates under identical gradients.

The actual step-122962 model and optimizer files were downloaded from Drive
and checked against their checkpoint hashes. All 30 resized parameter tensors
preserve old moment values exactly and have zero moments in added coordinates.
A discarded CPU update on four unchanged original examples advanced the grown
optimizer to122963 with finite gradients and weights. The original optimizer
stayed at122962 and both parent file hashes remained unchanged. No candidate
checkpoint or public predictions were generated by this check.

Policy: each grown tensor keeps the mature parent's Adam step counter. Added
coordinates therefore share mature bias correction instead of a fresh Adam
clock. This is explicit and must be assessed in a bounded quality comparison;
the helper does not establish an optimal learning rate. Scheduler, random
state and consumed-row migration are not exercised by this isolated check.
Evidence is in optimizer-verification.json and check_optimizer.py. The active
GPU training run remains unchanged.

## Follow-up: real training save and resume

`check_resume.py` creates an independently hashed, temporary grown checkpoint
from step122962 and uses the actual training entrypoint twice on CPU. Each
interval completes one update, saves model/optimizer/coverage state, and
resumes from that save. Both intervals pass: optimizer steps122963/122964,
unchanged schedule origin92456, expected phase steps30507/30508 and128/256
additional original-row presentations. All eligible unique-row counts remain
unchanged during this intentional second-pass continuation. Parent files are
verified again after the probe; temporary weights are discarded.

The first attempt completed one training update but its post-update audit used
the wrong coverage-field name. That test-harness error was corrected and the
two-interval check rerun successfully. No GPU job was restarted. The probe
uses CPU FP32 and omits CUDA random-state restoration only in its local
harness, so it does not prove CUDA/BF16 trajectory equality or model quality.
See resume-verification.json for measured update times and learning rates.
