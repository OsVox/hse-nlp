# Оптимизации HW2 по материалам курса

## Что найдено в неделях 1–4

Просмотрены лекции четырёх недель и исходники семинаров 1–3. Номера ниже — страницы PDF, начиная с первой.

| Материал | Приём | Что сделано в HW2 |
| --- | --- | --- |
| Неделя 1, лекция, стр. 4 | Квантизация, дистилляция, speculative decoding перечислены в плане курса | Это перечисление будущих тем, а не готовая реализация. Дистилляция дополнительных таргетов запрещена условием HW2. |
| Неделя 2, лекция, стр. 35–43 | Greedy и beam search | Уже используется быстрый greedy; beam search запускается только для синтаксически некорректных ответов. |
| Неделя 2, семинар, `tokenize` | Батчевая токенизация и динамический паддинг | Сохранены. В инференсе токенизация теперь выполняется один раз, её результат используется при сортировке, основном проходе и повторной генерации. |
| Неделя 3, лекция, стр. 41–47 | Группировка по длине | Добавлено окно из 32 батчей при обучении, сортировка по длинам токенизированных вопросов и кода. Все примеры сохраняются. `--group-window 1` отключает группировку. |
| Неделя 3, лекция, стр. 46 | Mixed precision | Обучение: `--precision auto` выбирает BF16 на поддерживающем CUDA GPU, иначе FP16 с GradScaler; CPU/MPS используют FP32. Доступен явный выбор. В инференсе добавлены те же варианты; FP32 остаётся по умолчанию до проверки качества более низкой точности. |
| Неделя 3, лекция, стр. 42–44 | Adam, gradient clipping, накопление градиентов | Уже были в коде. Накопление позволяет вместить эффективный батч, но само по себе не гарантирует ускорение. |
| Неделя 3, семинар, обработка данных | Батчевая токенизация; сравнение числа процессов | Не добавляем процессы без замера: быстрый токенизатор уже обрабатывает батчи. |
| Неделя 4, лекция, стр. 12 | KV-кэш | Уже включён при генерации. Явно отключён при обучении и валидации с готовыми ответами, где последовательность обрабатывается целиком и сохранять кэш для следующего шага не нужно. |
| Неделя 4, лекция, стр. 6–9 | Flash Attention | Не включён: проверенная T5 в Transformers 4.53.0 сообщает `_supports_sdpa=False`; ноутбук использует ветку 4.x. Нужны отдельно проверенные версия библиотеки, маски T5 и GPU. Флаг не добавлен как будто он уже работает. |
| Неделя 4, лекция, стр. 13–15, 37–44 | Multi-Query Attention, MoE | Это изменения архитектуры с новым обучением, а не переключатели скорости для сохранённого T5 checkpoint. Не применены к существующим весам. |

Дополнительно убрана передача `loss` на CPU после каждого микробатча. Сумма накапливается на устройстве и читается при логировании. Это уменьшает принудительные ожидания GPU; отдельного численного ускорения этому изменению пока не приписываем.

Группировка меняет порядок обучающих примеров, поэтому новый запуск не обязан повторять прежнюю траекторию обучения. Она также тратит время на определение длин: уменьшение паддинга ещё не доказывает ускорение всего обучения. Сравнивать нужно при одинаковом бюджете обновлений, seed и данных, меняя один параметр за раз. Существующие веса, предсказания, метрики и результаты в ноутбуках не перезаписаны.

## Проверки 2026-10-15

Среда: локальный CPU, PyTorch 2.7.1, Transformers 4.53.0.

- 4 теста: сохранение примеров и уменьшение паддинга, выбор точности, forward/backward без KV-кэша и совпадение генерации с кэшем, восстановление порядка ответов с повторяющимися запросами.
- Реальный сохранённый checkpoint, первые 16 вопросов опубликованного test.parquet, batch size 8, max_new_tokens 64: FP32-ответы до и после изменений совпали **16/16**. Исходная версия — коммит `3c5cb90`.
- Одиночный CPU-прогон: 0,60 с до и 0,52 с после. Без повторений и смены порядка запусков это проверка работоспособности, а не надёжная оценка ускорения.
- На искусственном примере из 9 строк группировка уменьшила число позиций в дополненных до общей длины целевых батчах с 1 353 до 870 (включая полезные токены). Это проверка механизма, не замер на всём корпусе.
- На момент локальной проверки GPU ещё не использовался. Результаты последующей проверки приведены ниже. Прежние 39,09 с на T4 относятся к старому запуску.

Запуск тестов из корня репозитория:

## Сравнение на GPU

Перед экспериментом: гипотеза — снижение точности сократит время генерации; проверяем время и число изменившихся ответов при том же checkpoint, batch size и лимите токенов.

```sh
python -m homeworks.hw2.benchmark_precision --precision fp16
```

Скрипт выполняет два полных прогона и сохраняет отдельные CSV и `results.json` в `homeworks/hw2/precision_benchmark/`. Он не отправляет ответы боту. Для BF16 нужен поддерживающий GPU; результат на корпоративной карте нельзя выдавать за результат на T4. При изменившихся ответах нужна проверка качества; синтаксическая корректность не равна pass@1.

Для отдельного сравнения группировки при обучении используйте свежие разные `--output-dir`, одинаковый `--precision fp16` и остальные параметры, меняя только `--group-window 1` / `--group-window 32`. Для сравнения точности зафиксируйте окно и меняйте только `--precision`. Не продолжайте старый эксперимент в той же директории под видом нового.

MCP, корпоративный аккаунт; NVIDIA RTX PRO 6000 Blackwell Server Edition,
PyTorch 2.11.0+cu130, Transformers 4.53.0. Все исходники и вывод ячеек:

Генерация: одинаковый checkpoint, 1919 вопросов, batch 64, лимит 192 токена,
прогрев перед измерением. Два прохода с обратным порядком вариантов во втором.
Время включает токенизацию, генерацию, исправление синтаксиса и запись CSV;
загрузка модели и скачивание данных исключены. Сравнение 3c5cb90 → 93f1a5f.

| После, FP32 |11,240|0|

Разница FP32 около 1%, диапазоны двух запусков перекрываются: убедительного

предсказаний, но не доказывает корректность самих ответов.
